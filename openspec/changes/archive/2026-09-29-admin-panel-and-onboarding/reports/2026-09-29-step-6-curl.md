### `/admin` without the variable

The server starts with no `ADMIN_PASSWORD`:

```
$ curl.exe -s -i http://127.0.0.1:3311/admin
HTTP/1.1 503 Service Unavailable
cache-control: no-store
content-type: text/plain; charset=utf-8

the panel needs ADMIN_PASSWORD: fill the variable in the environment of the server and start it again
```

The panel refuses to start and names the variable, without a value, which is the first scenario of the spec. The same
run answers `503` to the readiness probe of `/api/admin/setup`, so the refusal is in front of the whole panel and not
only of its page.

### The login and the sixth attempt

```
$ curl.exe -s -o NUL -w "%{http_code}" -X POST -H "content-type: application/json" -H "origin: http://127.0.0.1:3311"
    -H "x-forwarded-for: 198.51.100.61" -d "@.data/curl-bad.json" http://127.0.0.1:3311/api/admin/login   # five times
attempts 1 to 5: 401 401 401 401 401

$ curl.exe -s -i -X POST -H "content-type: application/json" -H "origin: http://127.0.0.1:3311"
    -H "x-forwarded-for: 198.51.100.61" -d "@.data/curl-good.json" http://127.0.0.1:3311/api/admin/login
HTTP/1.1 429 Too Many Requests
cache-control: no-store
retry-after: 900

{"status":"locked","error":"too many failed attempts from this address; try again in 900 seconds"}
```

The sixth attempt carries the **right** password and is still refused, with `Retry-After: 900`, which is the second
scenario of the spec. The address is the one of the `x-forwarded-for` header (`TRUST_PROXY=1` in this run), so the
lockout is the one of that address and not of the machine:

```
$ curl.exe -s -i -X POST -H "content-type: application/json" -H "origin: http://127.0.0.1:3311"
    -H "x-forwarded-for: 198.51.100.62" -d "@.data/curl-good.json" http://127.0.0.1:3311/api/admin/login
HTTP/1.1 200 OK
set-cookie: cited_admin=<token>; Path=/; HttpOnly; SameSite=Strict; Max-Age=43200

{"status":"ok"}
```

The cookie carries `HttpOnly`, `SameSite=Strict` and the twelve hours of the design; it carries no `Secure` because
the request arrives over `http` on `127.0.0.1`, which is what `isSecureHost` decides.

## The two findings of this task, and what was done about them

The manual run found two real defects that the unit tests could not see, and both are fixed in the commit that
carries this report:

1. **The production build failed.** `npm run build` stopped with
   `TurbopackInternalError: Failed to write app endpoint /admin/business/page — the chunking context does not support
   external modules (request: node:fs)`. The cause was a client component (`components/admin/BusinessForm.tsx`)
   importing `topicsFrom` from `lib/settings/business.ts`, the module decision 9 gives to this change: that module
   reads the store, and the store reads `node:fs`, so the browser bundle asked for a Node module. The split of the
   topics into `lib/settings/topics.ts` — a leaf module with no import of its own, re-exported by
   `lib/settings/business.ts` so its interface does not move — leaves the client with the parsing and the server with
   the store. The build compiles and type-checks after the split, and the page of the business is served.
2. **The `Origin` check refused the requests of a same-origin client whose host is an address.** The login answered
   `403` to `curl.exe` with `origin: http://127.0.0.1:3311`, because the guard compared the header with the origin of
   `request.url`, which the server had built with `localhost`. `lib/admin/guard.ts` now compares the `Origin` with the
   origin of the `Host` header of the request (with `x-forwarded-proto` when a proxy sets it) and with the origin of
   the URL, which is the check the framework itself documents for a Server Action and the one a browser can satisfy:
   a page cannot forge the `Origin` of another origin, and the `Host` is the address the client asked for. The new
   case of `tests/admin-guard.test.ts` pins both directions: the same host passes, another origin does not.

The run above is the second run of the same command after those two fixes; the first one is not quoted as a success
and its failures are the two findings written here.
