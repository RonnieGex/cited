The quick start of both READMEs has seven lines:

```
1  git clone https://github.com/RonnieGex/cited.git
2  cd cited

4  cp .env.example .env
5  EMBEDDINGS_PROVIDER=fake npm run ingest -- samples/
6  EMBEDDINGS_PROVIDER=fake npm run search -- "¿Cuánto cuesta una afinación de bicicleta?"
```

runs task 10.1: an anonymous clone cannot work. The line was attempted inside the container and it fails as the design
predicts:

directory: the files a clone checks out, with no history, in a container that starts with no `.env` and no `.data/`,

## The defect this step found, and its fix

**The quick start did not work as first written.** With the original block (`npm run ingest -- samples/` right after
`cp .env.example .env`) a clean clone fails:

```
> cp .env.example .env
> npm run ingest -- samples/
Error: EMBEDDINGS_PROVIDER must be one of openai, ollama, fake; received an empty or unknown value.
    at resolveEmbeddingsProvider (file:///work/lib/embeddings/providers.ts:126:11)
```

The template has every value empty on purpose, so copying it makes the value of `EMBEDDINGS_PROVIDER` the empty string,
and the code refuses to run without a provider. The task says the quick start must work on a clean clone, so the README
and the demo now carry the provider in front of the two commands:

```
EMBEDDINGS_PROVIDER=fake npm run ingest -- samples/
EMBEDDINGS_PROVIDER=fake npm run search -- "¿Cuánto cuesta una afinación de bicicleta?"
```

and the paragraph under the block says why, and how to keep it for the whole session by writing the line in `.env`
once. Both variants were verified in the container: inlined in the command, and appended to `.env`. Commit `76dd511`
carries the fix in both READMEs, in the render script and in the test, and the render script now patches the two
output blocks of the quick start from its own run, so the README cannot show an output the code does not produce.

## The CI workflow badge while the repository is private

```
> curl.exe -sI https://github.com/RonnieGex/cited/actions/workflows/ci.yml/badge.svg
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
```

The anonymous reader gets **404**, which is what the design predicted: the repository is private until the launch and
the badge renders only for readers with access. It is the seventh badge of the README, and the file `docs/readme-assets.md`
says so (task 9.1).

## The two READMEs through the GitHub Markdown API, with no token

```
> node markdown-api.mjs
README.md:    HTTP 200, 18891 chars of HTML, <h1> true, <picture> true, Cited true, katalis.dev true, token none
README.es.md: HTTP 200, 19229 chars of HTML, <h1> true, <picture> true, Cited true, katalis.dev true, token none
```

Both files render: the API returns the HTML of the banner (`<h1>` with the `<picture>` of the two themes), the name
`Cited` and the link to `katalis.dev`. No token was used.

**A note on the tool.** The contract says "one `POST https://api.github.com/markdown` of each README without a token",
and that is what was done. The first attempts used `curl.exe --data-binary @<file>` from PowerShell and the API
answered `403` with "The requested text is too large to render via the API" for a body of 14 KB; the same body sent
with `fetch` from Node answers `200`, and a 500-character slice sent with `curl.exe` also answers `200`. The failure
is in how the local `curl.exe` of this machine hands the file to the API, not in the API and not in the README: the
request is the same POST to the same endpoint with the same JSON and no token. It is recorded here as a RISK of the
local shell, not as a failure of the verification.
