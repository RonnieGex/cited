## The Linux container

The mount of the worktree does not work inside Linux (its `.git` is a file that points to a Windows path, which is the reason the report of
step 5 used a clone), so the run is over a plain clone of the branch, the same as CI checks out:

```
$ git clone --branch feature/brand-identity-ui <worktree> <temp>/clone           # HEAD 4246271
$ docker run --rm -v <temp>/clone:/src:ro node:24 bash -c \
    "cp -r /src /work && cd /work && node -v && npm -v && npm ci --fetch-retries=6 --fetch-timeout=180000 && npm test"
v24.21.0
11.19.0
 Test Files  78 passed (78)
      Tests  868 passed | 2 skipped (870)
```

The two skipped tests are the ones of `tests/design-system.test.ts` that skip on Linux by their own guard and that this change never touched. The clone
has its real `.git`, so the guard of the dependencies compared with `main` and the guards that call `git ls-files` ran; the committed list of the
dependencies of `main` (`tests/fixtures/dependencies-of-main.json`) covers the case where git cannot read it.

The first attempt of `npm ci` inside the container failed with `ETIMEDOUT` reading the registry (the machine was running other containers); the same command with
`--fetch-retries=6 --fetch-timeout=180000` installed everything and is the run above. It is a network matter of the moment, not of the tree: the second run of `npm ci`
resolved the same `package-lock.json`.
