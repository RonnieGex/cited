## 0. Katalis standard (prevails)

This repository is part of the Katalis suite and follows `docs/katalis-sdd-standard.md`, the canonical standard of
the suite copied byte by byte into this repository. Read and obey it before any change.

Where the Katalis standard and the specboot documents of this repository disagree, the Katalis standard wins. The
known difference is the reports path: reports live in
`openspec/changes/<change>/reports/YYYY-MM-DD-step-N-<name>.md` inside the change folder, not in
`specs/<change>/reports/`.

## 1. Core principles

- **Small tasks, one at a time**: work in baby steps. Never go forward more than one step.
- **Test-driven development**: every new behavior starts as a failing test, written before the code.
- **Type safety**: all code is fully typed. `any` is not used; `unknown` is narrowed before it is used.
- **Clear naming**: names carry the meaning. The code carries no comments; when a decision needs explaining it goes
  in `design.md` or in `docs/`.
- **Incremental changes**: prefer focused changes over large rewrites.
- **Question assumptions**: state what is verified and what is not.
- **Honesty in the reports**: a validation is written only after running the exact command.

## 2. Language standards

- **English only** for technical artifacts: code, identifiers, error messages, logs, documentation, README (except
  its Spanish part), specs, tests, configuration, scripts, commit messages and `LOOP_STATE.md`.
- **Exceptions**: the Spanish part of `README.md`; `docs/katalis-sdd-standard.md`, which is a byte-identical copy of
  the canonical standard of the suite and is therefore written in the language of the original; and the delivery
  documents that live outside this repository, in `katalis-dev/tasks/`.

## 4. Project skills and agents

- Agent definitions live in `ai-specs/agents/` and are the canonical source: `backend-developer.md`,
  `frontend-developer.md` and `product-strategy-analyst.md`.
- The tool folders `.claude/`, `.codex/` and `.cursor/` are generated by `openspec init` and `openspec update`. They
  are not edited by hand: the OpenSpec workspace is updated with the CLI, and `ai-specs/` holds what the CLI does not
  own.
- The `agents` entry of each tool folder is a symbolic link to `ai-specs/agents`, as the Katalis standard requires.
  It is not edited by hand either: `ai-specs/agents/` is the only place where an agent definition is written.
- When a request matches a skill of `.claude/skills`, load its `SKILL.md` before continuing, and load the referenced
  files the skill asks for.

## 5. Planning model requirement

Planning workflows (`enrich-us`, `openspec-ff-change`, `openspec-continue-change`) run best with a high-reasoning
model. This repository is executed by agents whose model is chosen by the operator; when the available model is not
the strongest one, the agent compensates with the full artifact set (`proposal.md`, `specs/<capability>/spec.md`,
`design.md`, `tasks.md`) and never skips an artifact because of the model. Do not stop to ask about the model;
continue with the workflow.

## 6. Stack rule

The repository is one Next.js application in TypeScript: the page, the API routes and the agent run in the same
process. Nothing of another repository is imported as code. A module is ported only after it is reviewed here, and a
module that comes from a private repository is rewritten, never copied.

Never in this repository: the Lufga font or any other commercially licensed font file; the book of Construye; golden
cases; holdout data; prompts of clients; prices; keys.

## 7. Mandatory OpenSpec artifact updates after `/apply`

A change requested after `opsx:apply` (or `/apply`) and before `opsx:archive` (or `/archive`) is a spec update first,
not a quick fix. The specification is the source of truth.

Required order:

1. Update the OpenSpec artifacts the request touches: scenarios, requirements and `tasks.md`. Add the work where it
   belongs in the design, not as an appendix of bugfixes.
2. If an artifact must be regenerated, run the OpenSpec step (`opsx:continue`, `opsx:ff` or equivalent) before
   coding.
3. Implement only after the artifacts carry the request.
4. Re-run the verification against the updated artifacts before archiving.

A code-only fix in this window is forbidden.
